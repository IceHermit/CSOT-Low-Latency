# Week 3 Project — Fastest Correct Parallel Tick Aggregator

> **Mission:** Implement a **single `aggregator.cpp`** that reduces a huge binary tick stream into a fixed per-symbol table of integer aggregates — `count`, `sum_price`, `min_price`, `max_price`, `sum_qty` — **correctly**, **deterministically**, and **as fast as four cores allow**. Week 1 taught you to measure one core; Week 2 taught you to feed its cache. Week 3 is where you use *all* the cores — and learn that threads only pay off if you stop them from racing, false-sharing, and getting shuffled by the kernel. Same "fastest correct implementation" game, a workload built to reward going wide.

## Build Instructions
- Navigate to `week-3/project`
- Run `cmake -B build -DCSOT_AGG_SRC=aggregator.cpp && cmake --build build -j`. This builds the `aggregator.cpp` script.
- Run `perf stat ./build/agg_runner data/tiny.ticks`. This runs the built `aggregator.cpp` on `tiny.trace` and returns the performance stats.
- If you want to run the simulator on a larger dataset, run `python3 data/gen_ticks.py --accesses 5000000 --seed 42 --out data/large.ticks`, then `perf stat ./build/agg_runner data/large.ticks`

## Working of the Multi-threaded Aggregator

- The script creates as many threads as there are available cores on the hardware (by checking the value of `std::thread::hardware_concurrency()`).
- There are two types of variables used in this method: global read-only variables, and local read-write thread variables: <br>
The global variables like `current_ticks_`, `current_n_`, `num_symbols_` are made to be read-only so that the threads do not fight over the value to be written to the variable.<br>
The variables local to the thread `auto* __restrict my_table = partial_tables_[t].table.get();` are free to be written and read by the processes on that thread. The final values of these variables are read by the parent thread during the Merge Phase.
- The variables for each thread are divided by index ranges: `(current_n_ * t) / num_threads_` to `(current_n_ * (t + 1)) / num_threads_`
- The Merge Phase simply accumulates all of the individual thread results. An important requirement of this step is the condition that the operation (addition, max, min etc.) must be commutative and associative, which is to say given a list of operands, the order of operands must not change the final result. We are keeping track of the `count`, `sum_price`, `sum_qty`, `min_price` and `max_price`, all of which satisfy the condition. If we were to, say, evaluate a power tower a1^(a2^(a3^....^an)))), we could not have used multi-threading.
- An important optimization was to avoid false-sharing, ie. when multiple threads attempt to access the same cache line. This spikes the number of L1 and L2 misses, and actually makes the program perform worse than a single-threaded program. This was avoided by using `alignas(64)` to introduce padding to every set of bytes a single thread uses, which makes sure each of these sets of bytes lives on a separate cache-line.

## Interesting Observations
The variance of the throughput in this week's script was way higher compared to previous weeks. When I was implementing threading for the first time, the throughput varied anywhere from ~300 M/s to ~700 M/s. This goes to show that threading is highly unpredictable if not implemented properly. Although this variance was reduced by the final iteration of `aggregator.cpp`, the throughput still sometimes drops to ~600 M/s, which could be because of noise. <br>
Multi-threading is a powerful beast that can ruin your performance if not tamed properly.
